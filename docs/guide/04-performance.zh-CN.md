# 4 · 性能：速度从哪里来

[指南目录](README.zh-CN.md) · [English](04-performance.md)

## 4.1 一个公式

```
实际速度 = 帧率 × 每帧码字数 × 每码字载荷 T × 捕获率 × 码字成功率 ÷ (1 + 喷泉开销)
             └──── 发送端决定：理论速率 ────┘   └───── 接收端决定 ─────┘   └ ≈ 0 ┘
```

- **理论速率**：演示发送端显示的"理论速率"，假设每一帧都被完整收到。
- **捕获率**：发送端的帧中被接收端拍到并识别过的比例（演示接收端诊断行里的"捕获"）。
- **码字成功率**：拍到的帧里解出的码字比例（"成功率"）。
- **喷泉开销**：恢复 K 个源符号平均需要 K + 1.6 个符号（最大的源块为 K + 2.4 个；见规范附录 C.2），大文件可以忽略。

所有提速手段都是在提高其中某一项。

## 4.2 设备实测

以下为维护者于 2026-11-03 报告的设备测试结果，不是按每帧容量推算的理论速率，也未与其他动态码协议进行同条件实测。

| 发送设备 | 接收设备 | 测试中达到的速度 |
|---|---|---|
| 电脑 | iPhone 应用 | 约 0.5 MB/s |
| Android 应用 | iPhone 应用 | 约 100 KB/s |

2026-11-17 在同一套设备上按下面的条件重测（接收端改为每个相机帧都识别、限制曝光时间、发热不降速之后）：

| 发送端设置（60 帧/秒，中等纠错） | 理论速率 | 接收时速率 | 码字成功率 | 每格相机像素 |
|---|---|---|---|---|
| 密度"高"，4 色 | 849 KB/s | 844 KB/s | 99% | 4.3 |
| 密度"极高"，4 色 | 1.3 MB/s | 1.23 MB/s | 90–94% | 3.5 |
| 密度"极高"，4 色，低纠错 | 1.4 MB/s | 1.29 MB/s | 86–89% | 3.5 |
| 密度"高"，8 色 | 1.2 MB/s | 1.09–1.2 MB/s | 82–94% | 4.0–4.3 |
| 密度"极高"，8 色 | 2.0 MB/s | 0.3–0.5 MB/s | 20–24% | 3.4 |

条件：桌面应用在 27 英寸 4K 60 Hz 液晶显示器上全屏播放；iPhone 15 Pro 应用手持接收，1080p、每秒 120 帧、曝光上限 1/1000 秒；文件为随机数据（不可压缩），数值是接收面板显示的接收时速率在 20 秒左右的稳定段内的读数。同一条件下改动前密度"高"为 470–730 KB/s。一次完整传输（95.4 MB，默认设置即"极高"4 色）用时 127.7 秒，整文件平均 765 KB/s，其中约 20 秒在对准，中途手机移动过一次；稳定段为 1.0–1.1 MB/s（每格 3.2–3.4 像素）。

这些数值表示测试中达到过的速度，不代表所有设备的持续平均速度。设备性能足够时，可以提高播放帧率以提升传输速度；实际效果还取决于屏幕、相机、拍摄距离和光线。

目前未随这两项结果记录完整的设备型号、软件版本、播放帧率、文件大小、压缩情况、计时口径和重复测试日志，因此不能据此计算对其他协议的性能倍数。复测时应记录这些条件，并分别报告接收时速率与文件完成后的平均速度，尤其避免把压缩带来的原文件速率与链路速率混用。

## 4.3 七个来源

### ① 每格更多比特（× 2 或 × 3）

QR 每个模块只有黑白，1 比特。Lumen Code 用颜色：C4 每格 2 比特，C8 每格 3 比特。C8 的三个比特直接对应 R、G、B 三个通道，一个通道判断错只错 1 比特。

默认不用 C8，是因为颜色越多，相邻颜色在相机里越接近，对模糊、摩尔纹、白平衡也越敏感。在模拟的"手持、没对准"测试中，C4 的码字成功率约 86–89%，C8 约 60%。C4 × 0.88 = 1.76 比特/格，比 C8 × 0.6 = 1.8 比特/格只少一点，但稳定得多。

### ② 更多格子（形状跟随屏幕，大小跟随物理尺寸）

- **形状**：QR 是正方形，而手机屏和相机画面都是长方形，正方形在 16:9 的区域里最多只占 56% 的面积。Lumen Code 的网格可以是任意 X × Y。参考发送端直接铺满屏幕（宽高比 ≤ 2.4），手机竖屏时就是一个细长的竖向码，格子比限制在 16:9 时多约 25%。
- **大小**：QR 的模块数由版本决定，和屏幕无关。Lumen Code 按屏幕的**物理尺寸**选格子大小，每格约 0.75 mm，接近 1080p 相机在正常距离下能分辨的极限。所以笔记本屏能放 3.6 万个格子，是 QR v25 的 2.65 倍。

### ③ 结构开销低

真实尺寸的帧中，数据格子占 92.6%（手机）到 95.3%（笔记本）。扣掉 RS 校验（16%）、每个数据包 7 字节的包头包尾和填充，**文件载荷占全部格子比特的 75–77%**。

### ④ 纠错按屏幕-相机信道定制

- 每个码字独立做 RS(n ≤ 255) 纠错，纠错等级可选 10% / 16% / 22% / 30%；
- 接收端用颜色分类的置信度找出最可疑的字节，当作擦除重试，等于把"软信息"用到了 RS 译码上；
- 每个数据包有 CRC-16，所以激进的擦除重试也是安全的，错误数据进不了喷泉解码器。

### ⑤ 码字独立 + Hilbert 排布：半张帧也有用

QR 一帧要么全部解出，要么作废。Lumen Code 每帧有十几到几十个独立的码字，沿 Hilbert 曲线各占一块紧凑区域。撕裂帧（相机拍到一半旧帧、一半新帧）、一块反光、一角失焦，都只损失那块区域里的码字（见 [指南 1](01-how-it-works.zh-CN.md) 的码字分布图）。实际拍摄中，这种部分可用的帧占很大比例。

### ⑥ 喷泉码：每一帧都是新数据

循环播放时，接收端必须收齐每一个分片，漏掉一个就要多等一整轮。漏帧率为 p、一轮 N 帧时，平均需要的轮数（等于时间倍数）：

| 文件帧数 N | 丢 10% | 丢 20% | 丢 30% |
|---|---|---|---|
| 10 | 1.76 | 2.32 | 2.93 |
| 46 | 2.41 | 3.25 | 4.17 |
| 150 | 2.93 | 3.97 | 5.14 |

喷泉码只要收到足够多的不同符号，时间倍数约为 1 / (1 − p)：丢 20% 时 1.25 倍，与文件大小无关。文件越大、丢帧越多，喷泉码的优势越大，上表范围内是 1.5 到 3.6 倍。

另外，接收端可以在任何时候开始扫描，中途移开再对准也不损失已收到的数据；文件描述符每 4 帧重复一次，随时都能拿到文件名。

### ⑦ 压缩

文本、JSON、日志、源代码在发送前用 DEFLATE 压缩，通常缩小到 1/3–1/5，相当于速度乘以 3–5。演示接收端完成后显示的"平均速度"按原始文件大小计算，所以传文本时会明显高于"接收速率"。

## 4.4 计算侧：让接收端跟得上

协议决定速度上限，接收端的计算速度决定实际能收到多少。如果识别一帧要 45 ms，而相机每 33 ms 给一帧、发送端每 83 ms 换一帧，接收端就会漏帧，还会发热。参考实现做了这些：

| 手段 | 效果 |
|---|---|
| 码在画面里时每个相机帧都识别 | 屏幕换帧是从上到下逐行进行的，液晶还要几毫秒才稳定，所以 60 帧/秒时任何一次拍摄都只有约一半的区域是干净的；相邻两次拍摄的干净区域互补，合起来接近 100% |
| 已解出的帧只读帧头 | 约 1 ms，而完整识别 5–9 ms |
| 同一帧前两次拍摄整帧读取，之后只解剩下的码字 | 拍摄可能在新帧头下带着上一帧的格子；某个码字位置解出的包如果和它上次给出的相同，就是旧帧，不记到新帧名下 |
| 曝光时间不超过发送帧周期的 1/16（60 帧/秒时 1/1000 秒） | 快门跨过换帧时刻的拍摄是两帧的混合；1/1000 秒比 1/500 秒每次拍摄多解出约 1/7，再短（1/2000、1/4000）则噪声占上风 |
| RS 译码查表，用生成多项式的余式判断码字是否干净 | 结果与原实现逐字节相同，一次识别中 RS 的耗时从 7.2 ms 降到 0.7 ms |
| 相机路径：亮度按格子大小平滑后每格只采样一次；分类从上一帧的色心和增益开始；对齐点在上一帧的位置附近找 | 一次识别从 18.2 ms 降到 4.7 ms（M2，377×198 的码），8 色多解出约 16% |
| 手机发热（fair、serious）时不降速，只在 critical 才限制识别并把相机降到 60 帧 | 一次传输只有一两分钟，降速正是用户想避免的损失 |
| ROI + 自适应分辨率（缩放到每格约 6 像素） | 像素量约 1/3，识别快约 2 倍，解码率不变 |
| ROI 裁剪和缩放交给 GPU（`createImageBitmap` 的裁剪与 resize 参数） | 不再拷贝、回读整帧 1080p，每次识别的准备时间约 3 ms |
| 收完后关闭相机；画面里没有码时降低识别频率；发送端不快时相机保持 30 帧/秒 | 阅读结果、放下手机时几乎不耗电 |
| 视频上方不用背景模糊 | 省掉 GPU 每个相机帧的一次全屏模糊 |
| Rust → WebAssembly | 比 JS 快 2.1–2.3 倍 |
| 多个 Worker 并行 | 手机 2 个，电脑最多 3 个 |
| 发送端 GPU 合成（每格 1 像素的画布 + 静态遮罩，GPU 放大） | 发送端每帧 CPU 开销接近零 |

在 Apple M2 上完整识别一张 1080p 照片：手机尺寸的码 JS 15–16 ms、WASM 7 ms；笔记本尺寸的码 JS 33 ms、WASM 14 ms。原生应用的相机路径（Y'CbCr，不要求与 JS 逐位一致）识别 377×198 的码 4.7 ms，473×248 的码 7 ms；iPhone 15 Pro 上分别约 5 ms 和 9 ms。

## 4.5 实际限制速度的是什么

按影响从大到小：

1. **格子在相机画面里的像素数**。原生应用实测（60 帧/秒，4 色）：≥ 4 像素成功率 99%，3.5 像素 90–94%，3.2–3.4 像素 80–86%，3.0 像素以下迅速掉到一半以下。1080p 画面里"极高"密度最多 4.0 像素/格（码正好撑满画面时），所以它要求码占满大部分画面。它取决于屏幕上的格子大小、拍摄距离和相机分辨率。"密度"调高后每帧数据更多，但格子更小，成功率会下降。
2. **相机**：发送帧率最好是相机"不合并像素"最高帧率的一半，这样每帧能拍到两次。实测（MacBook 内置 120 Hz 屏到 iPhone 15 Pro，相机 120 帧）：发送 60 帧时 766 KB/s，发送 120 帧时只有 80–400 KB/s，因为每帧只拍到一次，而且大多压在换帧过渡上；这台手机的 240 帧模式只有合并像素的版本，色度糊到相邻格子上，一个码字也解不出。多数手机网页只能拿到 30 帧/秒；卷帘快门导致撕裂；运动模糊。
3. **显示器**：帧率的上限是屏幕刷新率（应用按实测的刷新率给出上限，没有写死的数值；协议本身的上限是每秒 240 帧，因为帧序号只有 8 位）。60 Hz 屏幕上帧率最好是 60 的约数，否则每帧的显示时长忽长忽短。液晶屏换帧有几毫秒的过渡，接收端靠每帧拍两次来覆盖。
4. **接收端算力**：诊断行中"捕获"低于 80%、同时引擎耗时很高，就是算力不够，应换 WASM 或降低识别分辨率。

调优顺序：先保证成功率（格子像素数 ≥ 4.5、成功率 ≥ 90%），再提高帧率，最后才考虑提高密度或换 C8。有余量时，接收端会提示"识别有余量：可把发送端帧率提高到约 N"。

## 4.6 各环节的实测耗时

方法：`node test/bench.js`（JavaScript，Node 22）和在 `src/rust` 中运行 `cargo run --release --example measure -- bench`（Rust，原生）。每个值是预热一次后多次重复的平均值。机器：Apple M2 Pro，macOS 26.5。T = 200 字节；RS(255, 215) 是大网格的默认码字。

| 环节 | JavaScript | Rust |
|---|---|---|
| RS 编码，一个码字 | 12.8 µs | 8.0 µs |
| RS 译码，无错码字 | 33 µs | 33 µs |
| RS 译码，20 个错误字节 | 87 µs | 75 µs |
| 喷泉码：一个编码符号 | 1.2 µs | 0.12 µs |
| 喷泉码：从 K + 10 个符号解 K = 1000 | 8.4 ms（24 MB/s） | 0.8 ms（250 MB/s） |
| 喷泉码：从 K + 10 个符号解 K = 16 384 | 105 ms（31 MB/s） | 20 ms（164 MB/s） |
| 生成帧的格子，150 × 240 C4（34 个码字） | 0.76 ms | 0.76 ms |
| 解压（2.2 MB 文本的 zlib 流） | 147 MB/s | — |
| 接收端，从数据包完成 2 MB 的传输（10 064 个数据包） | 168 ms（12 MB/s） | 25 ms（79 MB/s） |

接收端处理数据包和解码的开销远小于识别（§4.4）：在 100 KB/s 的相机链路上，识别之后的全部处理只占一个核的约 1%。

## 4.7 还能更快吗？改进路线

改进按是否要改协议分为三类。不改协议的随时可以做，并且兼容所有现有实现。

### A. 只改接收端（不改协议）

| 改进 | 原理 | 预期收益 | 难度 |
|---|---|---|---|
| **跨帧软合并** | 同一帧通常被拍到 2–3 次，目前每次独立解码。改为把多次拍摄中同一格子的颜色似然相加后再分类，单次都解不出的码字合起来可能解得出 | 边缘条件（格子 3.4–4.5 像素）下成功率明显提高，大约相当于密度能再调高一档 | 中 |
| **去模糊 / 串扰均衡** | 模糊让每个格子混入邻居的颜色；用测得的模糊核做一次均衡（每格减去邻居的加权贡献） | **试过，不做**：在每格 3.5 像素的真机帧上拟合出的串扰几乎为零（中心 1.03，邻格 0.02 以下），均衡后只多解 2%，耗时多 30% | — |
| **去掉过渡带的影响** | 60 帧/秒时每次拍摄约 45% 的区域处在换帧过渡中。已知上一帧内容时，可以按混合比例把它减掉，只用一次拍摄解出整帧 | **暂不做**，见下 | 高 |
| **GPU 或 SIMD 识别** | 采样与分类高度并行 | **暂不做**，见下 | 高 |

### B. 只改发送端（不改协议）

| 改进 | 原理 | 预期收益 |
|---|---|---|
| 与刷新率对齐的帧率 | 120 Hz 屏幕上用 20、24、30 帧/秒，每帧显示时长恒定 | 撕裂更少，可用更高帧率 |
| 按接收端提示调参 | 没有回传通道，但人可以看接收端提示调整帧率、密度 | 已实现（提示"可把发送端帧率提高到约 N"） |

### C. 改协议（1.0 不采用，留给以后的版本）

| 改进 | 原理 | 代价 | 建议 |
|---|---|---|---|
| 帧头纠错码 | 给帧头加 BCH 或短 RS 码 | 每份副本多 21–35 格；帧格式变化 | **不采用**：实测帧头读不出时，最好的副本通常错 15–30 位（读的位置就偏了），纠错码只能救约 1/4。改为接收端"沿用上一个正确帧头"（已实现，不改协议），在同一测试中拿到了完美纠错码的全部收益（C4 码字成功率 +3.7 个百分点） |
| LDPC / 软判决码替代 RS | 直接利用每个格子的颜色置信度，编码增益约 1.5–2 dB | 解码复杂度高，实现难度大 | 留给 v2 |
| 更多颜色（C16） | 每格 4 比特 | 相机颜色分辨能力不够，成功率会大幅下降 | 不建议 |

### 目前决定不做的两项（2026-11-17）

**GPU 或 SIMD 识别。** 实测算力不限制速率：iPhone 15 Pro 上一次识别 4–10 ms，每秒 120 帧全部处理完，速率卡在相机帧率和屏幕换帧上，算得再快也不会多收一个包。采样、分类、亮度平滑占一次识别的约 2/3，适合并行，所以它们的价值是降低发热，而不是提高速率。出现下面任一情况时再做，并且先做 SIMD（留在同一份 Rust 代码里，各平台一起受益），GPU 放在后面（每个平台要各写一套，回读有延迟，GPU 自己也发热）：

- 接收面板里"识别"次数低于"相机"帧数，或"捕获"低于 100% 而成功率正常；
- 手机有了不合并像素的 240 帧或 4K 120 帧，识别量变成现在的 2–8 倍；
- 手机发热后单次识别超过约 25 ms（3 个识别线程在每秒 120 帧时的上限）。实测极高密度下发热后是 17–19 ms。

**减掉换帧过渡带。** 收益没有数据，风险有四个：混合不是线性的（液晶上升和下降速度不同，和前后颜色有关，相机输出也不是线性的），模型对不上某块屏幕时白花算力；上一帧没解出的区域没法减，漏帧会在同一区域连着传几帧；对近似随机的数据多做一次 RS 尝试，误纠且通过 CRC-16 的机会随之增加，而文件校验拦住它的代价是整个传输重来；单次识别估计多 30–50%。要做的话，先重新抓 60 和 120 帧/秒的原始帧离线验证，并且只把它作为失败码字的第二次尝试，这样最坏只是多花算力，不会少收包。

其余的 A 类改进里，跨帧软合并仍然值得做：不用改协议，直接提高成功率。帧头格式维持现状，已在 1.0 冻结。
